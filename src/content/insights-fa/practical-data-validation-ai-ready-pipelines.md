## اجرای موفق، به معنی صحت داده نیست

گاهی زمان‌بند اعلام موفقیت می‌کند، API پاسخ ۲۰۰ می‌دهد و عملیات واردکردن داده هم به‌موقع تمام می‌شود. اما آیا مطمئنیم **تمام اطلاعات رسیده، کلیدها تکراری نیستند و مجموع‌ها با منبع مستقل مطابقت دارند؟**

پایش عملیاتی به سؤال «آیا کار اجرا شد؟» پاسخ می‌دهد. اعتبارسنجی داده می‌پرسد «آیا مجموعه دریافت‌شده برای این کاربرد مشخص قابل‌اعتماد است؟» ممکن است پاسخ سؤال اول مثبت و پاسخ سؤال دوم منفی باشد.

این مقاله **آموزش فنی مستقل** است، نه گزارشی از عملکرد یک شرکت یا سامانه عملیاتی. تمام منابع، اعداد، شناسه‌ها و زمان‌های مثال ساختگی‌اند.

![عبور داده‌های فرضی از گیت‌های اعتبارسنجی تازگی، یکتایی و تطبیق](/images/ai-ready-data-validation-gates.svg)

سه کنترل را بررسی می‌کنیم: **تازگی، کلیدهای تکراری و تطبیق اطلاعات**. در انتها هم مشخص می‌کنیم اگر کنترل‌ها شکست خوردند، سیستم پایین‌دستی باید چه رفتاری داشته باشد.

## ۱. ابتدا قرارداد داده را تعریف کنیم

فرض کنیم هر صبح از دو منبع فرضی `north` و `south` برای یک **بازه گزارش‌گیری بسته‌شده** تراکنش دریافت می‌کنیم. هر ردیف چهار فیلد دارد: `source` (منبع)، `transaction_id` (شناسه)، `loaded_at` (زمان دریافت UTC) و `amount_cents` (مبلغ صحیح برحسب سنت).

یک **Manifest مستقل از همان داده دریافتی** انتظار ما را مشخص می‌کند:

| منبع | تعداد مورد انتظار | مبلغ مورد انتظار (سنت) |
| --- | ---: | ---: |
| north | ۲ | ۲٬۰۰۰ |
| south | ۱ | ۲٬۰۰۰ |
| **کل** | **۳** | **۴٬۰۰۰** |

رکوردهای معتبر نمونه:

| منبع | شناسه | ساعت دریافت UTC | مبلغ |
| --- | --- | --- | ---: |
| north | N-100 | 07:50 | 1,250 |
| north | N-101 | 07:50 | 750 |
| south | S-200 | 07:54 | 2,000 |

زمان بررسی **۹ نوامبر ۲۰۲۶، ساعت ۰۸:۰۰ UTC** است و برای آموزش حداکثر تأخیر دریافت را **۳۰ دقیقه** در نظر می‌گیریم. این اعداد سیاست عمومی یا SLA واقعی نیستند.

دو نکته مهم داریم: Manifest نباید از همان Dataset ناقص محاسبه شود؛ و «کامل‌بودن» باید نسبت به یک بازه مشخص سنجیده شود. اگر داده همچنان در حال دریافت است، به سیاست مشخصی برای تأخیر قابل‌قبول یا Watermark نیاز داریم. همچنین ذخیره مبلغ با عدد صحیح از خطای اعشاری جلوگیری می‌کند.

## ۲. تازگی هر منبع را جداگانه بسنجیم

آخرین زمان `loaded_at` را برای **تک‌تک منابع الزامی** بررسی می‌کنیم:

- `north`: آخرین دریافت ۱۰ دقیقه پیش؛ قابل‌قبول.
- `south`: آخرین دریافت ۶ دقیقه پیش؛ قابل‌قبول.
- اگر `south` اصلاً اطلاعاتی نفرستاده باشد، تازه‌بودن `north` نباید باعث موفق‌شدن کل Batch شود.
- اگر آخرین دریافت `north` ساعت ۰۷:۰۰ باشد، با محدودیت ۳۰ دقیقه رد می‌شود.

این آزمون فقط **تازگیِ دریافت داده** را می‌سنجد، نه زمان وقوع رویداد تجاری یا کامل‌بودن همه پارتیشن‌ها. رکوردی که همین حالا دریافت شده شاید مربوط به چند روز قبل باشد. برای این موضوع باید زمان رویداد و پوشش بازه‌ها را جدا بررسی کنیم.

مستندات [dbt Freshness](https://docs.getdbt.com/reference/resource-configs/freshness) درباره آستانه‌های `warn_after` و `error_after` توضیح می‌دهد. در این مقاله برای روشن‌بودن منطق، یک Validator کوچک مستقل می‌نویسیم.

## ۳. تکرار رکورد؛ چرا حذف خودکار راه‌حل خوبی نیست؟

تصور کنید به‌دلیل ارسال مجدد، `(north, N-101)` دو بار دریافت شود. تعداد خام از سه به چهار ردیف می‌رسد و مجموع از **۴٬۰۰۰** به **۴٬۷۵۰ سنت** تغییر می‌کند.

در SQLite برای جدول فرضی `staging_events` می‌توان از این کوئری استفاده کرد:

```sql
SELECT source, transaction_id, COUNT(*) AS occurrences
FROM staging_events
GROUP BY source, transaction_id
HAVING COUNT(*) > 1;
```

این کوئری کلید تکراری `(north, N-101)` را برمی‌گرداند. البته **کلید تجاری هر پروژه متفاوت است**؛ شاید برای ردیف سفارش، ترکیب شماره سفارش و شماره ردیف لازم باشد.

قبل از بررسی نباید بی‌سروصدا تمام رکوردهای مشابه را حذف کنیم. ارسال دوباره یک درخواست با ثبت نسخه اصلاحی متفاوت است. باید سیاست روشن برای Idempotency، نسخه‌بندی و برخورد با تناقض داشته باشیم. مستندات Great Expectations هم بین یکتایی یک ستون و کلید مرکب تفاوت می‌گذارد.

## ۴. تطبیق با Manifest مستقل

حتی مجموعه‌ای تازه و بدون کلید تکراری ممکن است ناقص باشد. لازم است **تعداد و مجموع مبلغ هر منبع در بازه مشخص** را با انتظار مستقل مقایسه کنیم:

```sql
WITH manifest(source, expected_rows, expected_cents) AS (
  VALUES ('north', 2, 2000), ('south', 1, 2000)
),
observed AS (
  SELECT source, COUNT(*) AS actual_rows,
         COALESCE(SUM(amount_cents), 0) AS actual_cents
  FROM staging_events
  GROUP BY source
)
SELECT m.source, m.expected_rows,
       COALESCE(o.actual_rows, 0) AS actual_rows,
       m.expected_cents,
       COALESCE(o.actual_cents, 0) AS actual_cents
FROM manifest AS m
LEFT JOIN observed AS o ON o.source = m.source;
```

با تکراری‌شدن `N-101`، تعداد `north` برابر **۳** به‌جای **۲** و مجموع آن **۲٬۷۵۰** به‌جای **۲٬۰۰۰** خواهد شد؛ هر دو باید باعث رد داده شوند.

این SQL یک **گزارش تشخیصی** است و به‌تنهایی همه موارد نامعتبر را نمی‌گیرد. کنترل منبع غیرمنتظره، مبلغ یا تاریخ نامعتبر، `NULL` و کلید تکراری جداگانه لازم است. در SQLite، تابع `COUNT(*)` همه ردیف‌ها را می‌شمارد اما `SUM` مقادیر تهی را کنار می‌گذارد؛ پس کنترل نوع داده و غیرخالی‌بودن فیلدها ضروری است.

همچنین اگر بازپرداخت، ارز متفاوت یا مالیات داشته باشیم، قواعد واحد و علامت مبلغ باید قبل از تطبیق تعریف شده باشند.

## ۵. اجرای مثال عملی Python

برای اینکه فقط در حد توضیح مفاهیم نمانیم، یک **نمونه مستقل و بدون کتابخانه خارجی** به همراه تست ساخته‌ام:

[کد و تست‌های Data Validation در GitHub](https://github.com/ahmadrastibarzoki/personal-website/tree/main/showcases/data-validation)

از ریشه مخزن با Python نسخه 3.10 به بالا اجرا کنید:

```bash
python showcases/data-validation/demo.py
python -m unittest discover -s showcases/data-validation/tests -v
```

استفاده ساده از تابع اصلی:

```python
from datetime import datetime, timezone
from demo import clean_rows, validate_batch

report = validate_batch(
    clean_rows(),
    {"north": (2, 2000), "south": (1, 2000)},
    as_of=datetime(2026, 11, 9, 8, 0, tzinfo=timezone.utc),
)
print(report["status"])  # PASS برای داده ساختگی سالم
```

این تابع Schema، نوع مبلغ، Timestamp دارای منطقه زمانی، منبع غایب یا غیرمنتظره، کلید تکراری، تازگی هر منبع و اختلاف تعداد و مبلغ را بررسی می‌کند. نتیجه فقط یک گزارش `PASS` یا `FAIL` است. در اجرای دوم برنامه یک ردیف تکراری اضافه می‌شود و خروجی شکست کنترل‌ها را نشان می‌دهد.

**حد این مثال مهم است:** کد هیچ داده‌ای را ذخیره، اصلاح، حذف یا منتشر نمی‌کند. اصالت Manifest را هم تأیید نمی‌کند. در پروژه واقعی باید کنترل‌کننده معتبر، تراکنش پایدار، نسخه‌گذاری، مدیریت تلاش مجدد و لاگ ممیزی جداگانه داشته باشیم.

## ۶. هنگام شکست کنترل‌ها، AI چه رفتاری داشته باشد؟

اعتبارسنجی زمانی ارزشمند است که نتیجه آن روی مصرف داده اثر بگذارد:

| وضعیت | رفتار پیشنهادی پایپ‌لاین | رفتار سیستم AI |
| --- | --- | --- |
| PASS | انتشار Snapshot تأییدشده با نسخه و بازه مشخص | نمایش محدوده و تاریخ داده |
| WARN با مجوز قبلی | ثبت استثنا و محدودیت | اعلام محدودیت و کنترل اقدام حساس |
| FAIL | قرنطینه Batch و نگهداری آخرین داده سالم | استفاده‌نکردن از داده ردشده به‌عنوان داده معتبر |
| UNKNOWN | فرض‌نکردن موفقیت بررسی‌نشده | بیان نبود شواهد کافی |

نمونه Python ما فقط `PASS` و `FAIL` را پیاده‌سازی می‌کند؛ `WARN`، `UNKNOWN`، قرنطینه واقعی و اتصال به مدل، صرفاً **پیشنهاد طراحی** هستند.

در سامانه عملیاتی باید درباره اجازه استفاده از آخرین Snapshot سالم، قدمت مجاز آن، تلاش مجدد، انتشار اتمیک و سیاست مواجهه با داده نامعتبر تصمیم گرفته شود.

## ۷. کیفیت داده را چندلایه بررسی کنیم

پیش از استفاده از اطلاعات در مدل پیش‌بینی، داشبورد یا دستیار AI، این کنترل‌ها را در قرارداد داده قرار دهیم:

1. **ساختار:** فیلدهای ضروری، نوع‌ها و واحدها دقیق‌اند؟
2. **تازگی:** همه منابع لازم در بازه مجاز اطلاعات فرستاده‌اند؟
3. **یکتایی:** کلیدهای تجاری براساس سیاست نسخه‌بندی بدون تکرارند؟
4. **کامل‌بودن:** همه منابع و ردیف‌های مورد انتظار در بازه بسته‌شده رسیده‌اند؟
5. **تطبیق:** تعداد و مجموع‌ها به تفکیک منبع با انتظار مستقل مطابقت دارند؟
6. **ردیابی:** Batch، نسخه داده و علت اصلاح یا رد را می‌توان پیدا کرد؟
7. **تصمیم:** آیا شکست تست جلوی مصرف اشتباه داده را می‌گیرد؟

آزمون‌های آماده dbt شامل `unique`، `not_null`، `accepted_values` و `relationships` هستند. اما تطبیق با Manifest مستقل و قواعد خاص کسب‌وکار همچنان طراحی مکمل می‌خواهد.

قبولی تست روی چند ردیف ساختگی **اثبات صحت سامانه تولیدی نیست** و نباید آن را با ادعای کاهش درصدی خطا یا افزایش بهره‌وری اشتباه گرفت.
